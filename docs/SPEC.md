## 🎯 1. Назначение продукта

### 🎯 1.1. Цель

Review Auto Responder — автономный ассистент, который 24/7 собирает новые отзывы с сайта, определяет их тональность, генерирует ответ нейросетью и уведомляет оператора в Telegram. Демонстрация универсального паттерна «парсер + автономная AI-обработка».

Система помогает команде поддержки:

- принимать отзывы клиентов через публичный веб-интерфейс сайта;
- автоматически определять тональность (позитивный / негативный / нейтральный);
- генерировать уместный ответ от лица компании;
- уведомлять оператора о каждом новом отзыве для своевременного вмешательства;
- не отвечать на собственные сообщения (защита от бесконечного цикла автоответов).

### ⚠️ 1.2. Решаемая проблема

| Проблема | Последствие |
|----------|-------------|
| Ручной мониторинг новых отзывов | Оператор вынужден обновлять страницу каждые 5–10 секунд |
| Задержка ответа на негатив | Пока оператор не увидит отзыв — клиент ждёт; негатив копится |
| Полностью ручной ответ | Не масштабируется; стоимость растёт с объёмом отзывов |
| Один LLM-провайдер (legacy) | Жёсткая привязка к OpenAI; недоступен ключ — нет ответа |
| Промпт в коде (legacy) | Сложно варьировать тон/политику ответа без правки кода |

### 💡 1.3. Решение

Двухсервисная архитектура:

- **Сайт отзывов** — активный участник потока: хранит отзывы и их статус (`new`/`processed`), принимает ответы обработчика как дочерние комментарии. Статус на сайте — первичный Source of Truth «обработан ли отзыв».
- **Обработчик (worker)** — автономный поллер: опрашивает сайт, забирает отзывы со `status=new`, определяет тон (дешёвый словарный классификатор — без LLM), генерирует ответ через LLM-провайдер, пишет ответ обратно, шлёт уведомление в Telegram.
- **Локальный state-файл** — вторичный идемпотентный guard для окна до смены статуса (предотвращает повторные уведомления и повторную генерацию ответа).

Доработка относительно legacy-референсов:

- **Мультипровайдерность** — OpenAI / GigaChat / YandexGPT через единую абстракцию; смена провайдера через web-`/admin` без рестарта (точка вызова меняется, логика сохраняется).
- **Web-`/admin` (runtime-config)** — операторская панель на сайте: смена провайдера, модели, base_url, `yandex_folder_id` и промпта через браузер; применяется на следующем цикле опроса без рестарта. Секреты остаются в `.env`, runtime-параметры — в `config.json` (shared volume).
- **Промпт в файле** — `prompts/v1/system.md` вместо хардкода в `processor.py`; override через `/admin`.
- **Единый docker-compose** — site + db + worker с общим `WORKER_API_TOKEN` и shared volume для runtime-config.
- **`/health`** — эндпоинты готовности для Deployment Validation.
- **Server-side фильтр `?status=new`** — вместо клиентского фильтра по полному списку.

## 👥 2. Пользовательские роли

| Роль | Описание | Основной интерфейс |
|------|----------|-------------------|
| **Клиент** | Пользователь, оставляющий отзыв | Публичный Web UI сайта: форма отзыва, форма ответа на отзыв |
| **Оператор** | Сотрудник поддержки, получающий уведомления | Telegram: личные уведомления о новых отзывах с тоном и текстом |
| **Владелец/инженер** | Развёртывает и сопровождает систему | `.env`, `docker-compose.yml`, `DEPLOYMENT_GUIDE.md` |
| **Оператор-настройщик** | Меняет провайдера/модель/промпт в runtime | Web-`/admin` на сайте (токен `ADMIN_TOKEN`) |
| **Демо-зритель** | Смотрит конфигурацию без права изменения (презентация заказчику) | Web-`/admin` на сайте (токен `ADMIN_DEMO_TOKEN`, read-only) |

## 🎬 3. Пользовательские сценарии

### 📝 Сценарий 1: Клиент оставляет отзыв

**Кто:** Клиент
**Цель:** Оставить отзыв на сайте

**Шаги:**
1. Клиент открывает сайт отзывов.
2. Заполняет имя (необязательно) и текст отзыва.
3. Нажимает «Отправить».
4. Отзыв появляется в списке (форма обновляется без перезагрузки).

**Результат:** отзыв сохранён в БД со `status=new`; список отзывов обновлён.

### 🤖 Сценарий 2: Обработчик отвечает на отзыв

**Кто:** Обработчик (автономно)
**Цель:** Определить тон и сгенерировать ответ

**Шаги:**
1. Обработчик опрашивает сайт с интервалом `WORKER_POLL_INTERVAL`.
2. Получает отзывы со `status=new`.
3. Для каждого: определяет тон (словарный классификатор), генерирует ответ (LLM-провайдер или fallback), создаёт дочерний комментарий-ответ, переводит отзыв и ответ в `status=processed`.
4. Если настроен Telegram — отправляет оператору уведомление о новом отзыве.

**Результат:** отзыв получил тон, ответ и статус `processed`; оператор уведомлён.

### 📣 Сценарий 3: Оператор получает уведомление о негативе

**Кто:** Оператор
**Цель:** Вовремя отреагировать на негативный отзыв лично

**Шаги:**
1. Обработчик определяет тон нового отзыва.
2. Отправляет в Telegram сообщение: «Новый отзыв … Тон: <тон> … Текст: …».
3. Оператор видит уведомление и при необходимости подключается лично (например, товар доставлен повреждённым — ИИ не решит, оператор сможет).

**Результат:** оператор мгновенно узнаёт о новом отзыве без ручного мониторинга страницы.

### 🔁 Сценарий 4: Защита от self-reply

**Кто:** Обработчик (автономно)
**Цель:** Не отвечать на собственные ответы

**Шаги:**
1. Обработчик создаёт ответ от имени `AI_AUTHOR_NAME` со `status=new`.
2. На следующем цикле опроса этот ответ попадает в список `new`.
3. Обработчик распознаёт авторство по имени и переводит ответ в `processed` без генерации ответа.

**Результат:** бесконечный цикл автоответов предотвращён.

### 🧪 Сценарий 5: Тест трёх отзывов разной тональности

**Кто:** Владелец/инженер
**Цель:** Подтвердить корректную работу ассистента

**Шаги:**
1. Оставить на сайте три отзыва: позитивный, негативный, нейтральный.
2. Дождаться обработки (до `WORKER_POLL_INTERVAL` + время генерации).
3. Убедиться: тон каждого определён корректно; ответ сгенерирован; статус `processed`; (опционально) пришло Telegram-уведомление.

**Результат:** три отзыва обработаны, ответы и тоны зафиксированы.

## ⚙️ 4. Функциональные требования

### 🌐 4.1. Сайт отзывов

| ID | Требование |
|----|------------|
| F-SITE-1 | `GET /` — главная страница с формой отзыва и списком отзывов (Jinja2, автообновление) |
| F-SITE-2 | `GET /api/reviews` — список всех отзывов; опциональный серверный фильтр `?status=new` |
| F-SITE-3 | `POST /api/reviews` — создание отзыва/комментария (`parent_id` опционален; валидация существования родителя) |
| F-SITE-4 | `PATCH /api/reviews/{id}` — обновление `status`/`response`/`tone`; авторизация по `X-Worker-Token` |
| F-SITE-5 | `GET /health` — health-эндпоинт для Deployment Validation |
| F-SITE-6 | Потоковая самоссылка `parent_id` (комментарии на комментарии) |
| F-SITE-7 | Автоинициализация схемы БД при старте (idempotent) |
| F-SITE-8 | `GET/POST /admin` — операторская панель runtime-config с демо-RBAC на два токена: `ADMIN_TOKEN` — полный, `ADMIN_DEMO_TOKEN` — read-only, `AdminIdentity` с ролью, `admin_auth` (чтение — demo допущен) + `require_admin` (мутация → 403 для demo). Поля: `provider`, `openai_model`, `openai_base_url`, `yandex_folder_id`, `system_prompt_override`; пишет `config.json` в shared volume. UI-бейдж «Демо-режим: только просмотр» + disabled кнопка сохранения |

### 🤖 4.2. Обработчик (worker)

| ID | Требование |
|------|------------|
| F-WORK-1 | Основной цикл: опрос сайта с интервалом `WORKER_POLL_INTERVAL`, ожидание готовности сайта при старте |
| F-WORK-2 | `fetch_new_reviews` — получение отзывов со `status=new` (через серверный фильтр) |
| F-WORK-3 | `detect_tone` — словарный классификатор тона (без LLM) |
| F-WORK-4 | `generate_response` — генерация ответа через активный LLM-провайдер; fallback на словарные шаблоны при сбое/отсутствии ключа |
| F-WORK-5 | Мультипровайдерность: OpenAI / GigaChat / YandexGPT / «Свой» — выбор через `/admin` (runtime, без рестарта) |
| F-WORK-6 | Промпт в `prompts/v1/system.md` (не в коде); override через `/admin` (`system_prompt_override`) |
| F-WORK-7 | `create_review` — публикация ответа как дочернего комментария (`parent_id`, `AI_AUTHOR_NAME`) |
| F-WORK-8 | `update_review` — смена статуса родителя и ответа на `processed` (PATCH + `X-Worker-Token`) |
| F-WORK-9 | `is_ai_authored` — пропуск собственных ответов (защита от self-reply) |
| F-WORK-10 | Локальный state-файл (`state.json`): `notified_review_ids`, `processed_review_ids` |
| F-WORK-11 | Telegram-уведомление о новом отзыве (опционально; пропуск при отсутствии токена) |
| F-WORK-12 | Heartbeat для healthcheck (файл/метка обновляется каждую итерацию) |
| F-WORK-13 | `RuntimeConfig` — mtime-кеш `config.json` из shared volume; провайдер/модель/промпт применяются на следующем цикле без рестарта |

## 🛡️ 5. Бизнес-правила и ограничения

| Правило | Обоснование |
|---------|-------------|
| Тон определяется словарным классификатором, а не LLM | Экономия токенов и предсказуемость для простых случаев; LLM — только для генерации ответа |
| Ответ публикуется как дочерний комментарий, не в поле `response` | Сохранение threaded-структуры сайта (видно в дереве) |
| Статус на сайте — первичный SOT new/processed | Не полагается на бесконечно растущий локальный файл |
| State-файл — вторичный guard для окна до смены статуса | Идемпотентность уведомлений и генерации при ретраях/рестартах |
| `PATCH` токен-gated, `POST`/чтение открыты | Legacy-модель доступа; documented в SECURITY_NOTES |
| Секреты в `.env`, runtime-параметры в `config.json` через `/admin` | Ключи API не попадают в редактируемый файл/браузер; `/admin` — два токена (admin/demo) по демо-RBAC, мутации запрещены для demo на backend |
| Fallback при сбое LLM | Система продолжает отвечать (словарные шаблоны) даже без ключа/при сбое API |
| Не отвечать на собственные ответы | Предотвращение бесконечного цикла |

## ✅ 7. Критерии приёмки

- [ ] Единый `docker compose up --build -d` поднимает db + site + worker; сайт доступен, обработчик опрашивает.
- [ ] `GET /health` сайта → 200; healthcheck обработчика (heartbeat) → healthy.
- [ ] Три отзыва разной тональности (позитивный/негативный/нейтральный): тон определён, ответ сгенерирован, статус `processed`.
- [ ] Смена `WORKER_PROVIDER` (OpenAI ↔ GigaChat ↔ YandexGPT) — ответ генерируется через выбранный провайдер; при сбое — fallback.
- [ ] `/admin` меняет провайдер/модель/промпт в runtime — применяется на следующем цикле опроса без рестарта.
- [ ] Демо-RBAC: `ADMIN_TOKEN` допущен к мутациям; `ADMIN_DEMO_TOKEN` — только чтение (POST `/admin` → 403); прямой API-вызов с demo-токеном отклоняется на backend.
- [ ] Промпт читается из `prompts/v1/system.md` (правка файла влияет на ответ без правки кода); override через `/admin`.
- [ ] Сайт с `?status=new` отдаёт только новые отзывы.
- [ ] Обработчик не отвечает на собственные ответы (self-reply).
- [ ] Telegram-уведомление приходит при настроенном токене; пропускается без него.
- [ ] Deployment Validation пройдена в чистом окружении (отчёт PASS).
- [ ] Публичная документация самодостаточна (нет ссылок на внутренние артефакты APL).

## 📦 8. Границы первой производственной версии

**Входит (v1.0):**
- Сайт отзывов + обработчик, единый compose, мультипровайдерность, промпт-в-файле, web-`/admin` runtime-config, `/health`, server-side фильтр, Telegram, state-файл, fallback, APL-документация, Deployment Validation.

**Не входит (отложено за baseline v1.0):**
- Персистентное хранилище state вместо JSON-файла — для MVP достаточно `state.json` с volume.
- Retry с экспоненциальной задержкой на 429/5xx LLM — fallback покрывает сбой; retry — отдельное развитие.
- ~~RBAC на `POST /api/reviews`~~ — **реализовано в v1.5** (токенизированный демо-лимиттер с квотой; см. [SECURITY_NOTES §3–4](SECURITY_NOTES.md)). За baseline v1.0 — legacy-модель доступа.
- Заполнение поля `Review.response` — ответ публикуется дочерним комментарием (threaded); поле зарезервировано.
